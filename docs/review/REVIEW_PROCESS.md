# レビュー運用メモ（Claude Code 実装 × Codex レビュー）

このプロジェクトで導入した「Claude Codeが実装し、Codexが独立レビューする」クロスレビュー運用の型をまとめる。
初出: AS1 v2.7.2 公開前レビュー（2026-08-28〜29）。3巡で公開前ブロッカー(DOM XSS等)を解消してからVector登録へ。

## いつ使うか（重さの判断）

- **使う**: 外に出る成果物（公開アプリ・配布物・共有ドキュメント）。XSSやデータ破損を世に出すコストは、レビュー数巡のコストより桁違いに大きい。
- **使わない/軽くする**: 使い捨てスクリプト・内部限定の実験。この型は過剰になる。

## 役割の線引き

- 2つのAIは**対等な同僚**であり権威ではない。「レビュー通過＝安全」と過信しない（2モデルとも見落とす可能性はゼロでない）。
- **判断は人間が握る**: バージョン番号、ライセンス、公開文言、仕様のトレードオフなどは実装/レビューではなく本人が決める接点として残す。
- 実装側AIの自己評価は当事者バイアスがある前提で扱う。

## フロー

1. **実装（Claude Code）** → 実装前にレビューア事前レビュー（本人ルール）。
2. **セルフチェック（ハンドオフ前・安い順に必ず）**:
   - 版数/日付など文字列の grep（例: 旧バージョンの残存）
   - 未使用シンボルの静的スキャン（死蔵コード）
   - 自分の差分の通読（diff self-review）
   - 挙動系の分類器などは実データで検証
   ※ この工程を怠ると、grep一発で気づけた指摘でレビューが1巡増える。
3. **ハンドオフ（→ Codex）**: 対象コミットID＋差分範囲を明示して渡す。
4. **レビュー（Codex）**: 結果を後述の様式で `docs/review/` に Markdown で残す（会話logと違い資産になる）。
5. **修正（Claude Code）**: 受け入れ条件を満たすまで修正し、**受け入れ条件ベースで客観検証**（主観の「直った」で終えない）。修正が隣接挙動を壊していないか併せて確認。
6. **再ハンドオフ → 再レビュー** を、公開前ブロッカーが無くなるまで繰り返す。

## レビュー文書の様式（効いた型・踏襲する）

各指摘に以下を必ず付ける:

- **重大度**: P1（公開前ブロッカー）/ P2（公開前に直すべき）/ P3（軽微・整合性）
- **対象**: `ファイル:行` を具体的に
- **現状 / 期待**: 何がどうなっているべきか
- **推奨修正**: 最小修正と理想修正
- **受け入れ条件**: 検証可能な形で（例: 「メモ欄に `<img src=x onerror=alert(1)>` を入力しても文字列表示になること」）

末尾に **再レビュー観点**（diffで何を確認するか）を書いておくと2巡目が速い。

## 検証（実装側が受け入れ条件に対して行う）

- JS構文チェック（単一HTMLはinline script抽出→`node --check`）
- ローカルHTTP配信でブラウザ実載（`file://`はプロジェクト外だと静的化しJS実行されない点に注意→`python3 -m http.server`で配信）
- 受け入れ条件を実ページ/Nodeで再現テスト（XSSは生成DOMのimg要素数=0、CSVはテストベクタで列崩れ/式実行なし 等）
- 配布zipを再生成したら、**zip内のファイルにも修正が入っているか**を必ず確認

## この運用で実際に捕まえた例（AS1 v2.7.2）

- 「完成」と判断した状態に残っていた **DOM XSS**（実装側の自己レビューでは取りこぼした）
- 占有率の**仕様と実装の不一致**（スコアに直結）
- 実装側の修正が**新たに生んだ副作用**（占有率修正→静寂時スコアが止まる）

→ 独立した第三の目が効くのは「別モデルだから」以上に「実装の意図に縛られていないから」。
